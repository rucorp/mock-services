# Как участвовать в mock-services

Спасибо за интерес! Проект — моки банков и облачных касс по их официальным
протоколам. Цель — дать интегратору рабочий, честный и объясняющий ошибки стенд
**до** договора с провайдером.

## Чем можно помочь

| Тип вклада | Как |
|---|---|
| Дефект мока | Issue с шаблоном «дефект мока»: что сделали, что ожидали, что получили, версия/коммит, `curl`-воспроизведение |
| Расхождение с протоколом провайдера | Issue с шаблоном «расхождение с протоколом»: ссылка на официальный раздел доки (или скриншот с датой), поле, ожидаемое поведение |
| Новый провайдер | Issue-предложение: название, публичная документация API, есть ли у вас доступ к тестовому контуру |
| Код | PR по правилам ниже |
| Документация | PR в `docs/integration/*`, `docs/reference/*` |

## Правила для кода

1. **Zero dependencies.** Ядро и адаптеры работают на одном Node (>= 18) без npm-пакетов.
   Новые зависимости обсуждаются отдельно и почти всегда отклоняются.
2. **Фиделити важнее удобства.** Если провайдер отклоняет запрос — мок тоже
   отклоняет, с тем же (или документированным) кодом. «Удобные» отступления
   допустимы только за флагом конфигурации и с пометкой в README.
3. **Ошибка = DX.** Любой отказ: код + человекочитаемое объяснение + поле +
   подсказка + ссылка на официальный раздел доки (`core.createErrorCatalog`).
   Голые `400/500` без объяснения не принимаются.
4. **Тесты обязательны.** `npm test` должен быть зелёным; на новый сценарий —
   новый пункт в selftest соответствующего сервиса; на дефект — регресс-тест.
5. **Тесты не должны быть флаки.** Не опирайтесь на `sleep`, если можно
   дождаться события/состояния; используйте свободные порты (`:0`).
6. **Секреты и реальные данные запрещены.** Только фейковые креды и тестовые
   карты; персональные данные покупателей в примерах не использовать.
7. **Стиль:** 2 пробела, одинарные кавычки, `'use strict';`, модули CommonJS;
   комментарии — по делу, на русском с английскими терминами (как в репозитории).

## Как добавить нового провайдера (адаптер)

1. Создайте `services/<provider>-mock/server.js` на `packages/core`
   (образец — `services/tbank-mock`, `services/kassa-mock`).
2. Опишите в адаптере **только протокол**: маршруты, поля, коды ошибок, машину
   состояний, тестовые реквизиты. Инфраструктура — из ядра.
3. Заведите документацию провайдера в `docs/reference/<provider>/` (канонический
   каталог — как у существующих адаптеров, например `docs/reference/tbank/`):
   таблица «эндпоинт → официальный раздел доки → дата сверки → статус сверки».
   Пример заголовка `docs/reference/mybank/01-payment-api.md`:

   ```md
   # MyBank · Payment API — сверка с моком

   | Эндпоинт мока | Официальный раздел доки | Дата сверки | Статус |
   |---|---|---|---|
   | `POST /v2/Init` | https://developer.mybank.example/api/init | 2026-10-11 | сверено |
   ```

   Относительные ссылки между доками проверяются автоматически
   (`npm run check:links` входит в `npm test`) — битые ссылки CI не пропустит.
4. Напишите `services/<provider>-mock/selftest.js` со всеми сценариями контракта
   (успех, отказ, таймаут, дубли, отмена/возврат — по специфике провайдера).
5. Добавьте инструкцию «интеграция за 10 минут» в `docs/integration/<provider>.md`
   и запись в таблицу README.

## Процесс

1. Fork → ветка с говорящим именем (`fix/kassa-receipt-datetime`).
2. `npm test` локально.
3. PR: что изменилось, зачем, как проверяли, ссылки на доку/issue.
4. Реагируйте на ревью; CI (Node 18/20/22 + docker smoke) должен быть зелёным.

## Обновление базового образа (security patches)

Базовый образ и релизный образ закреплены дайджестами (F-37), чтобы повторная
сборка одной версии репозитория не получала другой base image. Обновляют пины
**только** отдельным PR с обоснованием (CVE/плановое обновление):

1. Новый дайджест `node:22-alpine`:
   `docker buildx imagetools inspect node:22-alpine --format '{{json .Manifest.Digest}}'`
   (или строка «Digest» на hub.docker.com/_/node для тега `22-alpine`).
2. Обновите `FROM node:22-alpine@sha256:…` в `Dockerfile` и запишите в PR дату
   и причину обновления.
3. Прогоните оба контура проверок:
   `npm test` и `node scripts/docker-smoke.js` (tbank-mock и kassa-mock обязаны
   стать `healthy`, persist/restore — работать при `--read-only`).
4. После публикации GHCR-образа обновите дайджест релиза в
   `docker-compose.include.yml` (`MOCK_IMAGE_DIGEST`, строка «Digest» на странице
   пакета `ghcr.io/rucorp/mock-services`) — это deployment artifact потребителей.
