## 0. Резюме для владельца (TL;DR)

**Проект в хорошей стартовой точке:** два рабочих адаптера на общем ядре, DX-слой
с подсказками, честная Token-подпись Т-Банка, живые строка-в-строку сценарии,
зелёные selftest-ы. Это уже лучшее, что есть на рынке по нише (готовых моков
эквайринга Т-Банка в открытом доступе нет — см. `docs/reference/tbank/06-ecosystem.md`).

**Но в текущем виде это «стенд Lovii», а не публичный продукт.** Три системных разрыва:

1. **Мок воспроизводит не провайдера, а использование провайдера Lovii.** Т-Банк —
   только схема «Мультирасчеты со сделкой» (Init без `DealId`/`CreateDealWithType`
   отклоняется — `services/tbank-mock/server.js`, `handleInit`), касса — контракт
   Ferma под агентскую схему чеков Lovii. Обычный интегратор с обычным эквайрингом
   на таком моке споткнётся на первом же Init.
2. **Найдены и подтверждены пробами 17 дефектов, 1 из них — класса «молча теряем
   деньги/документы».** Самые тяжёлые уже исправлены в этой ветке (§10):
   потеря недоставленных вебхуков после рестарта (A-2), параллельные дубли
   нотификаций (A-3), фискальные данные «из 1970 года» (A-12) и дубли номеров
   чеков (A-13), `Cancel` больше суммы платежа как успешный полный возврат (A-7),
   XSS на публичных страницах (A-14).
3. **Нет задела публичного сервиса:** нет изоляции арендаторов (один общий state,
   один `external_id`-реестр, одни креды на всех), нет аутентификации/лимитов
   на публичном контуре, нет CI/Dockerfile/community-файлов, репозиторий до сих
   пор **private**, а в коде и доках — внутренние имена Lovii (`ЛОВИ`, «ООО
   „Аксиома“», staging-домены, тикеты SZ/T-038).

**Рекомендация по стратегии:** не «открывать всё сразу», а сделать **v0.2 —
«провайдеро-нейтральный мок»** (plain acquiring + полная матрица 54-ФЗ + изоляция
песочниц + сценарное API), и только потом публиковать как hosted-сервис.
Self-hosted дистрибуция (Docker/npx) может выйти раньше hosted-версии — она не
требует изоляции и защиты публичного контура.

**Оценка готовности к публичному запуску:** сейчас ~35%. После работ P0 из §9 —
~80% (можно открывать self-hosted и Preview-hosted с лимитами).

## 3. Готовность к публичности: продуктовый разрыв

### 3.1 Главный вопрос: что именно мы мокаем — провайдера или свой контур?

Сейчас в коде живёт **use case Lovii**, а не контракт провайдера:

- `Init` **требует** `DealId` или `CreateDealWithType=NN`, если передан
  `PaymentRecipientId` — это правило Мультирасчетов, а не эквайринга Т-Банка;
  обычный платёж без сделки (99% рынка) получит ошибку 7 на пустом месте.
- Касса моделирует агентскую схему Lovii (поставщик = лицензиат, агент =
  правообладатель) и знает только `sell`/`sell_refund`/`sell_correction`.
- Негативные сценарии завязаны на **соглашения об именах Lovii**:
  `external_id` с префиксом `fail-`/`hang-`. Публичный пользователь с
  `external_id = "order-42"` не получит ни одного негатива, а админ-кнопки
  не автоматизируются в CI.
- В ответах/лентах/доках светятся `ЛОВИ`, «ООО „Аксиома“», `mock-kassa-staging.lovii.ru`.

**Вывод.** Прежде чем открывать сервис, нужен слой «провайдеро-нейтральности»:
plain-режим по умолчанию + фирменные расширения Lovii (Мультирасчеты, агентские
чеки) — как конфигурируемый профиль. Это не переписывание: ядро уже правильное,
меняются дефолты и сценарный слой.

### 3.2 Изоляция песочниц — обязательное условие hosted-версии

Сегодня состояние глобальное: один `state`, один реестр `external_id`, один
терминал/касса. Два интегратора на одном публичном стенде гарантированно
пересекутся: чужой `external_id` → ошибка 12, чужие платежи в `/admin`,
чужой `PaymentId` читается `GetState` (авторизация-то — только по подписи
терминала, а он общий).

Проектное решение (детали — RFC-001, §9):

```
sandbox = { id, terminalKey, terminalPassword, fermaLogin, fermaPassword,
            state-partition, ttl, quotas }
запрос → идентификация песочницы (subdomain / заголовок X-Mock-Sandbox / ключ)
        → свой state + свой реестр external_id + свой /admin-token
        → reset/export по API, автоочистка по TTL, лимиты RPS и объёма
```

Для self-hosted режима всё это выключается одним флагом (одна песочница = весь стенд).

### 3.3 Сценарии — это продукт, а не кнопка в админке

Спека §1.3 обещает «сценарии отказов переключателем». Публичному пользователю
нужен **программируемый** сценарный API, детерминированный и пригодный для CI:

- управление сценарием в запросе: `X-Mock-Scenario: kkt-fail`, `webhook-500`,
  `timeout-30s`, `3ds-challenge`, `deadline-expired` (или поле в DATA);
- расписание и вероятности (`10% запросов — таймаут`) для нагрузочных проверок;
- **виртуальные часы**: `PUT /mock/time {offset: "7d"}` — чтобы тестировать
  авто-подтверждение холда (4/7 дней), `RedirectDueDate` (до 90 дней),
  авто-отмену (60 дней) и 36-часовое закрытие 3DS-сессии за секунды, а не сутками;
- журнал сценарных срабатываний (что и когда было включено) — иначе «почему
  мой платёж отклонился» превращается в археологию.

### 3.4 Ещё пять разрывов «внутренний стенд → публичный продукт»

| Разрыв | Сейчас | Надо |
|---|---|---|
| Дистрибуция | `docker compose up` из репозитория | Опубликованный образ `ghcr.io/...`, `npx mock-services`, один бинарь/контейнер; healthcheck; профили `bank`/`kassa`/`all` |
| Машиночитаемый контракт | Markdown + снятые HTML | OpenAPI 3.1 на оба адаптера + Postman-коллекция + готовые curl/JS/PHP-сниппеты; генерация примеров из спеки (спека §2) |
| Контракт-тесты интегратора (спека §1.4) | нет | CLI/сюита «прогони свою интеграцию против мока → отчёт о готовности» (проверка: подпись, идемпотентность вебхуков, дубли, ретраи, обработка отказов) |
| Демо-хостинг | нет | Публичный стенд-витрина: лендинг, кнопка «получить песочницу», лимиты, кнопка reset, без персистентности реальных данных |
| Сообщество | нет CI, CONTRIBUTING, issue-шаблонов | PR-гейт (`npm test` на 18/20/22), шаблоны issue («дефект мока», «расхождение с протоколом», «новый провайдер»), роадмап в Issues |

## 4. Протокольная полнота: Т-Банк (Эквайринг/Мультирасчеты)

### 4.1 Что реализовано и совпадает с докой

- `Init`/`Confirm`/`Cancel`/`GetState`/`CheckOrder` + нотификации с подписью;
  `SpAccumulationId` — только в нотификации `AUTHORIZED` и **участвует в Token**
  (сверено с конспектом `docs/reference/tbank/02-notifications-signature.md`);
- переходы `Cancel` по таблице банка (`NEW→CANCELED`, `АUTHORIZED→REVERSED/
  PARTIAL_REVERSED`, `CONFIRMED→REFUNDED/PARTIAL_REFUNDED`), идемпотентность по
  `ExternalRequestId`, «в NEW Amount игнорируется — отмена на полную сумму»
  (сверено со снятой страницей `/v2/Cancel`);
- критерий доставки нотификации «HTTP 200 + тело ровно `OK`», ретраи и дамп;
- `/e2c/v2/{Init,Payment,GetState}` (выплаты) и `/av/v1/{payment,verification}`
  (верификация счёта «прогон рубля»).

### 4.2 Чего не хватает (по убыванию рыночной востребованности)

| Приоритет | Метод/возможность | Зачем |
|---|---|---|
| **P0** | **Plain-режим без сделки** (Init без `DealId`/`CreateDealWithType`) | 99% интеграторов; сейчас это жёсткая ошибка |
| **P0** | `Charge` (рекуррент по `RebillId`) + `RebillId` в нотификации `AUTHORIZED`, `Recurrent=Y`, `AddCard`/`GetCardList`/`RemoveCard` | Подписки и «платежи в один клик» — второй по частоте кейс |
| **P1** | `FinishAuthorize` + `Submit3DSAuthorization`/`V2` (схема PCI DSS, без формы банка) | Интеграции, которые рисуют свою форму (или тестируют серверный 3DS-редирект) |
| **P1** | СБП: динамический QR (`Init` c `DATA.TinkoffPayWeb`/QR-методы), `GetQr`, минимальная сумма 10 ₽ | Самый быстрорастущий способ оплаты |
| **P1** | `SendClosingReceipt`/`Receipt`-объект в Init/Confirm/Cancel (ФФД 1.2, Items) и валидация `Receipt` — «чеки на стороне банка» | Связка «банк + ОФД» без внешней кассы |
| **P1** | `createSpDeal`/`closeSpDeal`, баланс сделки как валидатор выплат, `FinalPayout` один раз, запрет возврата после закрытия | Полнота Мультирасчетов (сейчас книга сделок декоративна и `/e2c` не проверяет баланс) |
| **P2** | Автоматика банка: авто-`Confirm` через 4/7 дней, авто-отмена неоплаченного заказа (60 дней), 3DS-сессия > 36 ч → `DEADLINE_EXPIRED` | Воспроизведение «времязависимых» сбоев (нужны виртуальные часы, §3.3) |
| **P2** | Чарджбэки по официальной нотификации (в доке Мультисплита их нет) + RRN/`GetOperationDetails` | Спорно: уточнить у банка, но `CHARGEBACK` уже эмулируется |
| **P2** | `/v2/getConfirmOperation`, `GetSbpMembers`, `QrMemberId` в Cancel, `PartnerId`-выплаты, acqapi-регистрация точек (mTLS) | Полная картина Мультирасчетов/выплат |

### 4.3 Замечания к точности

1. **`GetState.Amount` = остаток** после частичного возврата (`currentAmount`).
   В доке `Amount` — «сумма платежа»; в нотификациях — «текущая сумма». Нужно
   определиться и задокументировать, иначе интеграции, сверяющие
   `notification.Amount` с `GetState.Amount`, будут расходиться с боем.
2. **`CheckOrder` без `RRN`** — в доке поле присутствует; добавить (мок может
   генерировать стабильный фиктивный RRN по `PaymentId`).
3. **`NotificationURL` — только порт 443** (дока). Локально это мешает (и не
   должно мешать), но мок стоит **предупреждать** в журнале, что в бою такой
   URL не пройдёт.
4. **`RedirectDueDate` не валидируется** на границы «1 минута … 90 дней» —
   добавить ошибку 7 с подсказкой (сейчас любое значение просто парсится).
5. **`DATA` (≤ 20 пар, ключ ≤ 20, значение ≤ 100) и `Receipt` не валидируются** —
   проходит всё (в §4.2 P1 предложена валидация `Receipt`; `DATA` — дешёвая проверка).
6. **`IP` не используется** — ок для мока, но стоит принимать и показывать в журнале.

### 5.4 Риск достоверности контракта Ferma

Официальная документация Ferma закрыта личным кабинетом
(`docs/reference/external-links.md`: «401 без авторизации»), поэтому контракт

снять документацию в `docs/reference/ferma/` (как сделано для Т-Банка),

таблице соответствия. Если доступа нет — в README честно писать «контракт
воспроизведён по интеграции, сверка с первоисточником — в бэклоге», иначе это
репутационный риск.

## 6. Безопасность и эксплуатация публичного стенда

| Риск | Проявление | Мера |
|---|---|---|
| **Открытая админка (A-20)** | `/admin` показывает чужие платежи, `/admin/action` гасит чужую кассу (и CSRF: форма шлётся с любого сайта) | токен админки на песочницу (или basic-auth), CSRF-токен, `SameSite=Strict`, отключение админ-действий на hosted-контуре |

| **DoS/абьюз** | 1 ГБ тела запроса, бесконечные вебхуки, спам в `/admin` | лимиты тела (есть 5 МБ), rate limit по песочнице/IP, ограничение очереди вебхуков, TTL состояния, автоочистка |
| **Утечка данных между арендаторами (A-21)** | общий state и реестры | изоляция песочниц (RFC-001), отдельные креды, `/admin` scoped |

| **Публичный чек (A-14)** | XSS/фишинг через название позиции | экранирование (✅), `Content-Security-Policy: default-src 'none'`, `X-Content-Type-Options: nosniff`, отключение инлайновых стилей на hosted |
| **Обещание «не для прода»** | мок принимает всё, что похоже на боевой трафик | баннер в ответах/админке, `robots.txt`, отказ работать при реальных ключах (проверка префикса), явный `mode: hosted` |

Отдельно: `SECURITY.md` с каналом для репортов и заявление, что **все креды
фейковые** и **реальные карты использовать нельзя** — обязательный минимум для
публичного репозитория.

## 11. Приложение: как воспроизвести ключевые пробы

Пробы запускались на Node 22, локально, без внешних зависимостей:

1. **Рестарт очереди (A-2)** — два процесса с одним `MOCK_STATE_FILE`, вебхук
   отвечает 500: фаза 1 = 1 попадание, после рестарта 0 (до правки) / 1 (после).
2. **Дубли при медленном вебхуке (A-3)** — вебхук отвечает `500` через 3.5 с,
   `MOCK_RETRY_MS=1000`: до правки 16 POST при `attempts=4`; после — не более
   одного одновременного POST на запись.
3. **Чёрный ящик по API Т-Банка (A-5…A-9, A-15)** — короткий `Token`, `Cancel`
   сверх суммы, дубль `OrderId`, `GetState` по `OrderId`, чужой `TerminalKey`.
4. **kassa (A-10/A-12/A-13/A-14/A-11)** — `MOCK_PROCESS_MS=0`, два параллельных
   `sell`, страница чека с HTML в названии позиции, токен с истёкшим TTL.

Регрессы закреплены в selftest-ах (`npm test`), поэтому повторять пробы вручную
для этих дефектов больше не нужно.
