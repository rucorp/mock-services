# AGENT_RULES — регламент исполнителя (адаптация канона C)

> Источник: канон агентов «вариант C», репозиторий `bestdeejay-design/agents`
> (утверждён владельцем 03.11.2026, оркестрация саб-агентов — ADR-0002 от 06.11.2026,
> https://github.com/bestdeejay-design/agents). Версия адаптации и отображение на
> механизмы проекта — [ADR-0001](./decisions/2026-11-06-ADR-0001-canon-adoption.md).
> Регламент координатора — [COORDINATOR_RULES.md](./COORDINATOR_RULES.md).
> **При расхождении приоритет у файлов этого репозитория** (`AGENTS.md` §0);
> расхождения фиксируются в ADR, а не разрешаются исполнителем молча.

## 1. ARCA внутри цикла задачи

Каждая задача идёт по фазам **AUDIT → RESEARCH → CONCLUSION → ACTION → VERIFY**
(labels `phase:*`). Глубина зависит от размера (`size:*` ставит только координатор):

| Размер | AUDIT | RESEARCH | Гейт | Формат |
|---|---|---|---|---|
| `size:S` | мини-аудит вместе с `🎯 CONCLUSION` (3–5 строк) | не нужен | Fast-Track (ADR-0002): без паузы на `GATE OPEN` до кода | 1 проход дуэта |
| `size:M` | отдельный аудит (`AUDIT`) | варианты ≥ 2 + `REVIEWER_KICK` | координатор ставит `phase:action` | коллегия, смена ролей |
| `size:L` | как M | как M + ADR в `docs/decisions/` | как M, ADR `proposed` → `accepted` на гейте | ADR + 2 волны |

Для `M`/`L` до гейта запрещены реализация и PR. По канону исполнитель всегда
работает в свежем контексте (свежий саб-агент на роль) — при работе без механики
хаба (`spawn-pack`/`preflight`, см. ADR-0001 §«Ограничения») роли гейта и ревью
исполняют другие агенты/сессии, не автор.

## 2. Режимы исполнителя

Флаг `external` в issue = внешняя сессия (запущена владельцем вручную).

| Шаг | Внутренний агент | Внешний агент |
|---|---|---|
| Ветка | ветка поставки в этом репозитории | своя ветка (не `main`, не чужая) |
| Push | коммит → пуш ветки → письмо | обязателен после каждой задачи: только своя ветка |
| PR | создаёт сам, ссылка на issue, `Closes #N` | PR открывает координатор, если не сказано иное |
| Self-merge | разрешён при зелёных проверках и approve на точный коммит | запрещён: внешний не мержит никогда |
| Поставка | письмо в issue: диапазон коммитов + sha7 кончика | пуш ветки + письмо; канал — комментарий в issue |

Перед сдачей перечитай комментарии issue: свежий комментарий владельца старше
текста регламента; расхождение — в пользу комментария, с пометкой координатору.

## 3. Как брать задачу

1. Нужен issue со `status:ready` и твоим конкретным `to:*`; совпадение только по
   `agent:*` право брать не даёт. `to:sz-pool` берётся захватом (`✋ CLAIM` + перевод
   labels; в этом репозитории, без механики хаба, — комментарий `✋ CLAIM #N` и
   атомарная замена labels `status:ready`→`status:in-progress`, `to:sz-pool`→`to:sz-N`).
2. Проверь зависимости (нативная связь `blocked by`; строка `Depends on:` в теле —
   дубль). Расходятся — истина за связью, сообщи координатору.
3. Радиус аудита задан в issue. Выход за радиус — question координатору, не
   самовольное расширение. Нашёл баг/долг не по своей задаче — одна строка в отчёт
   поставки, чинить «заодно» нельзя.

## 4. Аудит и решение (AUDIT, RESEARCH, CONCLUSION)

- **AUDIT**: факты радиуса с `файл:строка`, зависимости и точки слома, долг зоны,
  актуальность документации. Только проверенное; «не знаю» — легальный ответ.
- **RESEARCH**: ≥ 2 реальных варианта с плюсами/минусами, сверка с принятыми ADR
  и `CONTRIBUTING.md`. Для `size:L` — ADR `proposed` в `docs/decisions/`.
- **CONCLUSION**: решение, понятное без контекста чата: «Что меняю» (точный
  список), «Что НЕ меняю», «Отвергнуто» (M/L), «Проверка» (как докажут результат),
  новый долг — явно назван или «нет».

## 5. ACTION: поставка

1. Ветка: `arena/<сегмент>-<тема>`, `fix/…` или `docs/…` от свежего `origin/main`
   (`git fetch --prune` перед стартом). В `main` не пушить.
2. Обязательные прогоны — по таблице `AGENTS.md` §2; минимум для любой поставки —
   `npm test` до начала (зелёная база) и перед сдачей. Красный регресс на своей
   ветке — пуш откладывается: сначала атрибуция на базовом коммите (A/B).
3. Один PR = одна логическая группа; в описании обязательны `Closes #N` и отчёт по
   схеме «что сделано / что НЕ сделано / развилки / риски / прогоны с выводом».
4. **Письмо-поставка** — комментарий в issue: диапазон коммитов, sha7 кончика,
   какие прогоны выполнены с финальными строками. Первая строка — маркер
   `📬 DELIVERED #N — поставка готова, ждёт ревью`. Без письма поставка не существует.
5. Heartbeat по размеру: S — каждые ≤10 минут движения, M — ≤30 минут, L — ежедневно.

## 6. Ревью и правки

- Ревьювер — всегда не автор. Вердикт: `🔎 VERDICT #N — approve <sha7>` или
  `🔁 REJECTED #N — правки: <первый пункт>`. Approve действителен только на точный
  sha7: новый коммит обнуляет вердикт.
- `🔁 REJECTED` — чини всё, а не первый пункт; вторая rejected подряд — задача
  снимается с исполнителя координатором.
- Слияние — координатор, только одобренный head-коммит.

## 7. Сигналы и гигиена

Словарь маркеров (`📬 DELIVERED`, `🏁 DONE`, `⛔ BLOCKED`, `❓ QUESTION`, `🔎 VERDICT`
и др.) — 1-в-1 из канона (KNOWLEDGE_BASE §5 хаба); маркер — первая строка
комментария, формат `<знак> <СЛОВО> #<номер> — <суть>`. Маркер без перехода labels
и переход без маркера — оба дефект; истина при расхождении — последний вердикт в
комментариях. Блокировка: `⛔ BLOCKED #N — блокер: …` + отдельный question-issue.
Секреты, PAN и ПДн — никогда в коде, тестах, логах и письмах.
