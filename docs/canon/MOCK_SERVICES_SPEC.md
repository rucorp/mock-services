# MOCK_SERVICES_SPEC — Опенсорс-проект «мок-банк + мок-касса»: сервис тестирования платёжных и фискальных интеграций

> Версия: v0.1.0 (2026-10-08) · Класс: C (инженерная спека) · Статус: черновик
> к обсуждению · Постановка: владелец 08.10 («создавай карточки и спецификации,
> будем создавать опенсорс проект») · Карточки: [`SZ-095`](TASKS/SZ-095-mock-bank-service.md),
> [`SZ-096`](TASKS/SZ-096-mock-kassa-service.md)

## 0. Идея в одном абзаце

Открытый сервис, который имитирует **банк-эквайринг** и **кассу/ОФД** по их
официальным протоколам — чтобы любой участник рынка (магазин, платформа,
интегратор) мог тестировать свою платёжную и фискальную интеграцию до
договора с банком/ОФД: с корректными схемами запросов, честными кодами
ошибок, управляемыми сценариями отказов и внятными подсказками «что не так
в вашем запросе и как это чинить». Seed-провайдеры — уже работающие моки
Lovii: `tbank-mock` (эквайринг Т-Банка) и `kassa-mock` (ОФД Ferma).

## 1. Целевая ценность (зачем это рынку)

1. **Тестируй до контракта.** Тестовые контуры банков и ОФД доступны только
   после договора и согласований. Мок даёт рабочий протокол сразу.
2. **Качественный вывод ошибок.** Реальные шлюзы возвращают сухие коды без
   контекста. Мок объясняет: какое поле невалидно, какой сценарий сломан,
   ссылку на пункт документации провайдера и рекомендацию.
3. **Сценарии отказов по кнопке.** Недостаток средств, таймаут шлюза,
   дублирование вебхука, отмена, чарджбэк, касса недоступна, ретрай после
   сбоя — всё это в реальности воспроизводится тяжело, тут — переключателем.
4. **Контракт-тесты как продукт.** Набор проверок «ваша интеграция
   соответствует документации провайдера» — прогон своей интеграции против
   мока = отчёт о готовности к боевому подключению.
5. **Расширяемость.** Ядро + адаптеры провайдеров: новые банки и ОФД
   добавляются декларацией протокола, без форка сервиса.

## 2. Архитектура (уровень намерения, не рецепта)

```text
┌─────────────────────────────────────────────────────┐
│  mock-services (отдельный сервис/репо)              │
│                                                     │
│  ┌────────────┐  ┌────────────┐  ┌───────────────┐  │
│  │ Ядро:      │  │ Адаптеры   │  │ DX-слой:      │  │
│  │ транзакции,│  │ провайдеров│  │ отчёты,       │  │
│  │ сценарии,  │  │ (bank:     │  │ подсказки,    │  │
│  │ вебхуки,   │  │ tbank, …/  │  │ контракт-     │  │
│  │ идемпотент-│  │ kassa:     │  │ тесты, инст-  │  │
│  │ ность      │  │ ferma,     │  │ рукции        │  │
│  │            │  │ atol, …)   │  │ интеграции    │  │
│  └────────────┘  └────────────┘  └───────────────┘  │
│        + панель сценария/наблюдения (web UI)        │
└─────────────────────────────────────────────────────┘
```

- **Ядро** — сущности «транзакция/чек», машина состояний, идемпотентность,
  доставка вебхуков (ретраи, подпись), журнал запросов.
- **Адаптер провайдера** = декларация протокола: маршруты, схемы полей,
  коды ошибок, машина состояний провайдера, соответствие официальной доке
  (ссылки на разделы доки в каждом ответе об ошибке).
- **DX-слой** — то, чего нет у реальных шлюзов: человекочитаемый разбор
  ошибки + рекомендация + deep-link на раздел доки; отчёт «готовность
  интеграции»; генератор примеров запросов (curl/SDK-снипеты).
- **Панель** — текущие транзакции/чеки, переключение сценариев, лог
  вебхуков с статусами доставки.

## 3. Скоуп MVP (что берём в первую волну)

| Компонент | MVP | Позже |
|---|---|---|
| Банк: протокол | эквайринг Т-Банка (Init/Confirm/Cancel/GetState + Notification) | Сбер, ЮKassa, PSB… |
| Банк: сценарии | успех, отказ, таймаут, дубль вебхука, отмена, чарджбэк | 3DS-эмуляция, сплит-платежи |
| Касса: протокол | Ferma (фискализация/отчёты/возвраты) | АТОЛ Онлайн, ОФД-операторы РФ |
| Касса: сценарии | печать, callback, отказ ККТ, повтор после сбоя | агрегатор нескольких ККТ |
| DX | код ошибки + подсказка + ссылка на доку | контракт-отчёт, SDK-снипеты |
| Хостинг | docker-compose, один контейнер | SaaS-версия с кабинетами |

## 4. Связь с Lovii

- `tbank-mock` (lovii-core, staging-extras, `mock-pay-staging.lovii.ru`) и
  `kassa-mock` (T-038, контракт Ferma, selftest 13/13,
  `mock-kassa-staging.lovii.ru`) — **первые адаптеры и источник проверенного
  кода**; Lovii остаётся первым потребителем и витриной проекта.
- Lovii не блокируется: свои моки живут в core, пока сервис не созреет;
  переключение на внешний сервис — отдельная миграция, не в этом цикле.
- Публичные подсказки в ответах мока не раскрывают ничего о данных Lovii.

## 5. Развилки (требуют решения владельца)

1. **Репо/имя:** отдельные репо `lovii-tech/mock-bank` + `lovii-tech/mock-kassa`
   vs монорепо `lovii-tech/mock-services` (ядро+адаптеры вместе) —
   рекомендация: монорепо, адаптеры = модули.
2. **Лицензия open-source:** MIT / Apache-2.0 — конфликт с
   COPYRIGHT_STANDARD Lovii и что с брендом «Лови» в публичном репо
   (рекомендация: Apache-2.0, нейтральное имя проекта).
3. **Стек:** стыковаться с существующим (`tbank-mock` — Node, `kassa-mock` — ?)
   vs единый стек ядра — решить по факту аудита двух моков.
4. **Публичность кода:** публиковать сразу в открытый GitHub vs довести в
   приватном репо до MVP и открыть по готовности (рекомендация: второе —
   открыть с рабочей докой и примерами).
5. **Публичный демо-хостинг** (например, `mock.services/...` или отдельный
   домен) — нужен ли на старте или только self-hosted.

## 6. Критерии качества (продуктовый стандарт проекта)

1. Каждый эндпоинт задокументирован **ссылкой на официальный раздел доки
   провайдера** (версия доки + дата сверки).
2. Ошибка = `{код, человекочитаемое объяснение, какое поле/шаг, рекомендация,
   ссылка на доку}` — никаких голых 400.
3. Машина состояний провайдера соблюдается и проверяется тестами (нельзя
   подтвердить неотменённый платёж, нельзя вернуть неотпечатанный чек).
4. Вебхуки: подпись, ретраи с расписанием провайдера, идемпотентность
   по event-id, журнал доставки.
5. Selftest-набор (как 13/13 у kassa-mock) обязателен на каждый адаптер.
6. README-инструкция «интеграция с нуля за 10 минут» на каждом провайдере.
