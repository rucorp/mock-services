## 0. Как пользоваться документом

- Каждая задача имеет ID (`MS-NN`), приоритет, место в репозитории, что сделать и критерий готовности.
- Приоритеты: **P0** блокирует публикацию; **P1** обязателен до публичного hosted-стенда (`POST /sandboxes` в интернете); **P2** улучшения.
- Метка **[VERIFY]** значит: автор аудита видел только документацию, а не код. Сначала проверьте, что проблема реально существует, и только потом чините. Если проблемы нет, закройте задачу тестом, который это фиксирует.
- Метка **[DECISION]** значит: нужен выбор владельца проекта. Агент не решает сам, а готовит варианты и спрашивает.

## 1. Контекст проекта

- Назначение: тестовые моки банков и касс по официальным протоколам (Т-Банк эквайринг, касса Ferma, ЮKassa `/v3`, АТОЛ Онлайн v4), чтобы интеграторы тестировали платёжные и фискальные потоки до договора с провайдером.
- Состояние: alpha 0.5.0, Apache-2.0, Node >= 18, **ноль зависимостей**, Docker-образ на `node:22-alpine`.
- Структура: `packages/core` (состояние, очередь вебхуков, журнал, редакция секретов, access-control, SSRF-проверки), `services/{tbank,kassa,yookassa,atol}-mock` (адаптеры-декларации), `protocols/*.json` (манифесты и детектор дрейфа), `scripts/`, `docs/{audit,rfc,canon,integration,reference}`, `.github/workflows/ci.yml`.
- Режимы: self-hosted (дефолт, без токенов, порты только на 127.0.0.1) и hosted (`MOCK_HOSTED=1`: fail-closed управляющая поверхность, owner-token песочницы, SSRF-политика, TTL и квоты).
- Тесты: `npm test` (core, tbank, kassa, yookassa, atol, upstream selftest, `check:drift`), `npm run test:compose`.

## 2. Правила для агента

1. Не меняйте протокольное поведение адаптеров (форматы, коды ошибок, подписи), если задача этого прямо не требует. Любое изменение сверяйте с `protocols/*.json`, `docs/reference` и запускайте `npm run check:drift`.
2. После каждой задачи `npm test` должен проходить. Новое поведение закрывайте тестом. Тесты без `sleep`-ожиданий и без фиксированных портов (требование `CONTRIBUTING.md`).
3. Зависимости не добавлять. Если без них никак, остановитесь и спросите владельца.
4. Никаких реальных секретов, ключей, карточных данных и персональных данных в коде, тестах, логах, примерах.
5. Один PR на логически связанную группу задач (см. раздел 9). В описании PR перечислите ID задач и результат проверки.
6. Каждое изменение env-переменных отражайте в `docker-compose.yml`, `docker-compose.include.yml`, README сервиса, `SECURITY.md` и `CHANGELOG.md`.
7. Если требование неоднозначно или две части документации противоречат друг другу, не угадывайте. Запишите вопрос в описание PR.
8. Не переписывайте историю git и не удаляйте теги без явного разрешения. Для задачи MS-07 (проверка истории) только готовьте отчёт.

## 3. Стратегия распространения (решение принято)

1. **Основа: self-host.** Образ в GHCR с тегами версий (`0.x.y`, `0.x`, `latest`), `docker compose up`, запуск одной командой без клонирования репозитория. Мок нужен в CI и локально, там важны воспроизводимость и закреплённая версия.
2. **Дополнение: один публичный демо-стенд** с `POST /sandboxes` для пробы «за 2 минуты». Запускать только после закрытия всех P0 и P1.
3. «Мы ставим вам» не отдельный формат, а платная услуга поверх self-host.
4. Документацию для интеграторов держать в `docs/integration/*.md` («интеграция за 10 минут»).

## 4. Задачи P0 (блокируют публикацию)

### MS-01. Релиз и образ в GHCR
- **Проблема:** `docker-compose.include.yml` по умолчанию тянет `ghcr.io/rucorp/mock-services:0.5.0`. **Уточнено координатором:** образ пересобирается на каждый push `main` и содержит все четыре сервиса; проблема — в другом: **нет тегированного релиза** (GitHub Release/SemVer), `0.5.0` одновременно и «текущий main», и старый релиз, а include-файл не зафиксирован на неизменяемом артефакте.
- **Сделать:** выпустить релиз с тегом (SemVer), опубликовать образ с тегами версий, обновить `MOCK_IMAGE_TAG` в include-файле, обновить `CHANGELOG.md`. В CI добавить шаг: `docker compose -f docker-compose.include.yml --profile mock config` и реальный `pull` опубликованного тега.
- **Готово, когда:** `docker pull ghcr.io/rucorp/mock-services:<tag>` работает без авторизации и все четыре сервиса стартуют из include-файла на этом образе.

### MS-02. Убрать подстановку чужих переменных окружения
- **Где:** `docker-compose.include.yml`.
- **Проблема:** конструкции вида `${MOCK_TERMINAL_PASSWORD:-${TBANK_TERMINAL_PASSWORD:-mockpass123}}` подтягивают переменные приложения-потребителя (`TBANK_TERMINAL_KEY/PASSWORD`, `TBANK_NOTIFICATION_URL`, `FERMA_LOGIN/PASSWORD/GROUP`, `YOOKASSA_SHOP_ID/SECRET_KEY`, `ATOL_LOGIN/PASSWORD/GROUP`). Если там боевые значения, они попадут в окружение мок-контейнера, в `docker inspect` и в состояние. Это противоречит `SECURITY.md`.
- **Сделать:** оставить только `MOCK_*` с безопасными дефолтами. Потребитель задаёт их явно в своём compose или `.env`. Описать это в `docs/integration/*.md`.
- **Готово, когда:** в include-файле нет ни одной переменной без префикса `MOCK_`, кроме технических (`COMPOSE_*`). Тест или CI-шаг делает `grep` по этому правилу.

### MS-03. Запуск контейнера не от root
> **Статус: выполнено (#37).** `USER mock:mock` (UID 10001), `/data` с правами и VOLUME, базовый образ запинен дайджестом, процесс bump — в CONTRIBUTING.
- **Где:** `Dockerfile`.
- **Сделать:** создать `/data`, выдать права пользователю `node`, `COPY --chown=node:node`, `USER node`. Закрепить базовый образ по дайджесту (`node:22-alpine@sha256:...`) и описать обновление дайджеста (Dependabot для docker или ручной процесс). Каталог `/data` создавать **до** первого подключения volume, иначе запись состояния упадёт с `EACCES`.
- **Готово, когда:** `docker compose run --rm tbank-mock id` показывает не root, запись в `/data` проходит, `docker compose up` на чистом volume работает, `test:compose` зелёный.

### MS-04. Усиление запуска в compose
- **Где:** `docker-compose.yml`, `docker-compose.include.yml`.
- **Сделать:** `init: true` (Node как PID 1 плохо обрабатывает SIGTERM), `read_only: true` + `tmpfs: [/tmp]`, `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]`, `pids_limit`. **[VERIFY]** что сервер при SIGTERM корректно закрывает listener и сбрасывает состояние на диск (`persist`), добавить тест.
> **[VERIFY] снят координатором (2026-10-12):** обработчиков `SIGTERM`/`SIGINT` в сервисах нет вообще. Порядок работ: сначала graceful shutdown (`server.close()` + `persist()`), затем `init`/`read_only`/`cap_drop`.
- **Готово, когда:** после `docker compose stop` и повторного `up` состояние (в том числе очередь вебхуков) сохранено, сервисы стартуют с `read_only`.

### MS-05. Лицензионные шапки
- **Где:** `SECURITY.md`, `docs/rfc/*.md`, README и все документы, где есть строка «все права защищены».
- **Проблема:** проект под Apache-2.0, а в документах «© ООО «Аксиома» … все права защищены» и «Документ проекта mock-services (оригинал: …)». Это противоречие.
- **Сделать:** заменить на `Copyright 2026 ООО «Аксиома». Licensed under the Apache License 2.0.` (как в compose-файлах), убрать строку «оригинал: …». Проверить `NOTICE`. Добавить SPDX-заголовки в исходники (`// SPDX-License-Identifier: Apache-2.0`).
- **Готово, когда:** `grep -ri "все права защищены"` по репозиторию пуст.

### MS-06. Токены не в URL
- **Где:** `packages/core` (`checkControlAccess`), `SECURITY.md`, RFC-001 §6–7.
- **Проблема:** допускаются `?operator_token=` и `/admin?token=<ownerToken>`. Токены из URL попадают в логи прокси, историю браузера и заголовок Referer.
- **Сделать:** при `MOCK_HOSTED=1` отклонять токен в query-строке. Для браузерной админки: однократный обмен токена на cookie `HttpOnly; SameSite=Strict; Secure` через POST. В self-hosted режиме оставить query-токен как deprecated с предупреждением в логе. Обновить документацию.
- **Готово, когда:** тест подтверждает: в hosted запрос с токеном в query даёт 401, с заголовком проходит, cookie-сессия работает.

## 5. Задачи P1 (до публичного hosted-стенда)

### MS-08. Разбор числовых env и тест «пустая строка»
- **Где:** `packages/core`, все `services/*/server.js`.
- **Контекст:** `flagEnabled(value, fallback)` уже покрывает boolean (`1/true/yes/on` против `0/false/no/off`, пустое = fallback). Include передаёт `MOCK_HOSTED: "false"` и пустые строки в `MOCK_SANDBOX_TTL_MS`, `MOCK_SANDBOX_MAX`, `MOCK_VIRTUAL_CLOCK`.
- **Проблема [VERIFY]:** `Number("")` равно `0`, то есть TTL песочницы 0 мс или максимум песочниц 0. Для чисел аналога `flagEnabled` в описании core нет.
- **Сделать:** добавить `numEnv(value, fallback, {min, max})`: пустая строка и `NaN` дают fallback, `0` допустим только там, где это осмысленно (например, `MOCK_PENDING_TTL_MS=0`). Заменить все ручные `Number(process.env.X)`. Таблица-тест в `test:core`: для каждой env из include-файла проверить значения `""`, `"false"`, `"0"`, мусор.
- **Готово, когда:** сервис с include-окружением по умолчанию ведёт себя так же, как без переменных, и это закреплено тестом.

### MS-09. SSRF: закрыть TOCTOU
- **Где:** `packages/core` (`assertPublicHost`, `postJson`, `createDeliveryQueue`).
- **Проблема:** `assertPublicHost` проверяет имя отдельно, а затем `postJson` резолвит его снова. Между проверкой и соединением DNS может вернуть другой адрес (DNS rebinding). `SECURITY.md` честно называет защиту best-effort.
- **Сделать:**
  1. Передавать в `http.request`/`https.request` собственный `lookup`, который резолвит имя и проверяет каждый адрес (`isPrivateAddress`) **внутри** callback, чтобы соединение шло ровно на проверенный IP.
  2. Покрыть диапазоны: IPv4-mapped IPv6 (`::ffff:127.0.0.1`), `169.254.0.0/16` (в том числе `169.254.169.254`), `100.64.0.0/10`, `0.0.0.0/8`, `fc00::/7`, `fe80::/10`, loopback, multicast, нестандартные записи IP (десятичные, восьмеричные, шестнадцатеричные).
  3. В hosted: allowlist портов (80/443, как в RFC §7), запрет схем кроме http/https, лимит размера читаемого ответа и общий дедлайн запроса (не только таймаут соединения).
  4. Тесты: резолвер, возвращающий публичный IP при проверке и приватный при соединении (rebinding), каждый перечисленный диапазон, редирект (клиент не должен следовать).
- **Готово, когда:** все перечисленные случаи блокируются в `test:core`. В `SECURITY.md` убрать оговорку про TOCTOU или заменить на актуальную.

### MS-10. Allowlist приватных приёмников вебхуков
- **Где:** `SECURITY.md` (таблица сценариев), `packages/core`.
- **Проблема:** для сценария «доступен команде по сети» рекомендовано `MOCK_BLOCK_PRIVATE_WEBHOOKS=1`, но приёмники команд почти всегда на приватных адресах. Защиту будут выключать.
- **Сделать:** добавить, например, `MOCK_WEBHOOK_ALLOW_CIDRS` (список разрешённых сетей и хостов поверх блокировки). Проверка allowlist идёт на уровне IP после резолва (внутри `lookup`, см. MS-09). Обновить таблицу в `SECURITY.md`. По умолчанию в hosted allowlist пустой.
- **Готово, когда:** при включённой блокировке вебхук на адрес из allowlist доставляется, на любой другой приватный блокируется. Есть тест.

### MS-11. Открытый редирект
- **Где:** обработка `SuccessURL`/`FailURL`, `return_url` и аналогов в адаптерах; RFC-001 §10.4.
- **Проблема:** мок редиректит браузер покупателя на URL из запроса. На публичном домене это инструмент фишинга.
- **Сделать:** в hosted разрешать только http/https, по возможности показывать промежуточную страницу с указанием целевого домена. Отклонять `javascript:`, `data:`, `file:`, URL с userinfo. Закрыть вопрос в RFC.
- **Готово, когда:** тесты отклоняют опасные схемы в каждом адаптере, где есть редирект.

### MS-12. Hosted: default-песочница fail-closed
- **Где:** `packages/core`, адаптеры, `SECURITY.md`.
- **Проблема:** без `MOCK_SANDBOX_TOKEN` песочница `default` остаётся открытой, сервис лишь пишет предупреждение. Управляющие маршруты при этом fail-closed. Непоследовательно.
- **Сделать:** при `MOCK_HOSTED=1` и пустом `MOCK_SANDBOX_TOKEN` отключить `default` (бизнес-маршруты без песочницы отвечают 404/401) или отказаться стартовать. Выбрать вариант и описать.
- **Готово, когда:** тест: hosted без токена не отдаёт `default`.

### MS-13. Лимиты создания и RPS
- **Где:** `packages/core`, `SECURITY.md`, RFC-001 §10.1.
- **Проверить [VERIFY]:** реализованы ли лимит создания песочниц на IP и RPS-квота на песочницу. В `SECURITY.md` перечислены TTL, `MOCK_SANDBOX_MAX`, `MOCK_SANDBOX_MAX_DOCUMENTS`, но не rate limit.
> **Статус (ревизия):** частично выполнено (#8) — лимит создания на IP (`MOCK_SANDBOX_CREATE_LIMIT`), `MOCK_SANDBOX_MAX`, TTL/sweep уже есть; осталось RPS-квота и `X-Forwarded-For`/`MOCK_TRUST_PROXY`.
- **Сделать:** если нет, реализовать: лимит `POST /sandboxes` на IP в сутки (предложение из RFC: 3), RPS-квота на песочницу, `MOCK_TRUST_PROXY` (учитывать `X-Forwarded-For` только от доверенного прокси, иначе IP подделывается). Задокументировать переменные.
- **Готово, когда:** массовое создание песочниц с одного IP упирается в лимит (тест), заголовок `X-Forwarded-For` от недоверенного источника игнорируется (тест).

### MS-14. Идентификаторы и изоляция
- **Где:** генерация id песочниц, `PaymentId`/uuid, RFC-001 §4, §7.
- **Проблема:** в RFC пример id `swift-fox-42` (человекочитаемый), а §7 требует ≥96 бит энтропии. Страницы без токена (confirmation у ЮKassa, чек `/receipts/{uuid}`, страница оплаты) в поддоменной схеме защищены только секретностью id.
- **Сделать:** для hosted использовать случайный id песочницы ≥96 бит (base32/ksuid), человекочитаемые имена только как алиас в `/admin`. **[VERIFY]** что `PaymentId` (у настоящего Т-Банка числовой) и uuid чеков не позволяют читать данные чужих песочниц и изолированы по песочнице. Тест на межпесочничный доступ по угаданному/последовательному id.
- **Готово, когда:** перебор идентификаторов не даёт доступа к данным другой песочницы (тест).

### MS-15. Канал сообщения об уязвимостях

- **Готово, когда:** в `SECURITY.md` есть конкретный адрес и ссылка на форму отчёта.

### MS-16. Заголовки безопасности HTML-страниц
- **Где:** `packages/core` (`html()`), страницы `/admin`, чеки, confirmation.
- **Сделать:** по умолчанию добавлять `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` (или `frame-ancestors 'none'`), `Content-Security-Policy` с `default-src 'none'` и точечными исключениями (inline-стили и скрипты только там, где они нужны). **[VERIFY]** что `escapeHtml` применяется и в контексте атрибутов, а значения для `href`/`action` от пользователя не допускают `javascript:`. Тесты на XSS в каждой странице, показывающей значения от интегратора.
- **Готово, когда:** заголовки видны в ответах (тест), XSS-пэйлоады экранируются во всех страницах.

### MS-17. Prototype pollution
- **Где:** `parseBody` (JSON и form-urlencoded), `restore()`/`mergeInto`.
> **Статус (ревизия):** в основном выполнено (#23) — restore/import/merge отклоняют `__proto__`/`constructor`/`prototype` на всех уровнях, тесты есть; остаток — `parseBody` (JSON/form).
- **Проверить [VERIFY]:** тело с ключами `__proto__`, `constructor`, `prototype` (в том числе вложенными и в виде `a[__proto__][x]=1` для form-urlencoded) не должно менять прототипы. `restore()` сливает файл «на месте» (`mergeInto`), его тоже нужно защитить.
- **Сделать:** фильтровать эти ключи при разборе и слиянии или использовать `Object.create(null)`. Тесты.
- **Готово, когда:** `({}).polluted === undefined` после отправки пэйлоадов всех видов.

### MS-18. Покрытие редакции секретов по адаптерам
- **Где:** `packages/core` (`classifyKey`, `redactSecrets`), тесты адаптеров.
- **Проблема:** класс поля определяется по имени, неизвестное считается `safe`. Новые адаптеры приносят свои секретные поля (`payment_token`, `secret`, `access_token`, `api_key`, `Token`, `pass`, ...).
- **Сделать:** для каждого адаптера составить список секретных полей из `protocols/*.json` и документации, прогнать через `redactSecrets` и убедиться, что все замаскированы. Оформить как тест, который падает при добавлении нового поля-секрета без маскирования (например, манифест помечает поля `secret: true`, тест их проверяет). Добавить требование в раздел «Как добавить нового провайдера».
- **Готово, когда:** тест перебирает секретные поля всех четырёх адаптеров и проходит.

### MS-19. Токены доступа: длина и подбор
- **Где:** `checkControlAccess`, запуск сервера в hosted.
- **Сделать:** в hosted отказываться стартовать, если `MOCK_ADMIN_TOKEN`/`MOCK_OPERATOR_TOKEN`/`MOCK_SANDBOX_TOKEN` короче 32 символов. Ограничить частоту неудачных попыток по IP (с учётом MS-13). Убедиться, что сравнение проходит по хэшам одинаковой длины (иначе длина токена утекает).
- **Готово, когда:** тесты: короткий токен блокирует старт в hosted, серия неверных попыток даёт 429.

### MS-20. Приём тел и таймауты сервера
- **Где:** `readBody`, создание `http.Server` во всех сервисах.
- **Проверить [VERIFY]:** при превышении `maxBytes` соединение закрывается (не дочитывается). Выставить `headersTimeout`, `requestTimeout`, `keepAliveTimeout`, `maxHeadersCount` (защита от slowloris). Лимит одновременных соединений в hosted.
- **Готово, когда:** тесты: большое тело обрывается, медленный клиент отключается по таймауту.

### MS-21. Журнал по песочнице для арендаторов
- **Где:** `/admin/journal`, `/sandboxes/me/*`, RFC-001.
- **Идея:** главная ценность проекта «как мок понял ваш запрос». В hosted сейчас журнал закрыт операторским токеном и арендаторам не выдаётся. Благодаря редакции и ограничению размера записи можно отдавать журнал **только своей** песочницы по owner-token (например, `GET /sandboxes/me/journal`).
- **[DECISION]:** включать ли это в hosted-стенд. Подготовить вариант и тесты изоляции.
