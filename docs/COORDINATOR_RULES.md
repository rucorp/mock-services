# COORDINATOR_RULES — регламент координатора (адаптация канона C)

> Источник: канон агентов «вариант C», репозиторий `bestdeejay-design/agents`
> (утверждён владельцем 03.11.2026, оркестрация саб-агентов — ADR-0002 от 06.11.2026,
> https://github.com/bestdeejay-design/agents). Адаптация и ограничения —
> [ADR-0001](./decisions/2026-11-06-ADR-0001-canon-adoption.md).
> Регламент исполнителя — [AGENT_RULES.md](./AGENT_RULES.md).
> При расхождении приоритет у `AGENTS.md`/`CONTRIBUTING.md` этого репозитория (§0).

Координатор — единственная точка входа задач: слово владельца становится брифом
только через него. Продуктовые решения — владелец.

## 1. Декомпозиция: issue

Один issue = один исполнитель = один проверяемый результат. Обязательный состав:

- первая содержательная строка тела: `Поставил: <роль/сессия> — <источник>`;
- бриф + измеримые критерии приёмки (issue без радиуса или критериев не публикуется);
- labels: по одному из закрытых групп `status:*`, `agent:*`, `to:*`, `type:*`,
  `size:*`, `priority:*`, `env:*` (для `type:question` — без `size:*`/`env:*`);
  ревьювер назван в теле; флаги (`external`, `needs-human`, `has-pr`, …) — по факту;
- радиус аудита и явный список «вне радиуса»;
- входные данные — ссылками (доки проекта, гайды провайдера, принятые ADR);
- зависимости: нативная связь `blocked by` + строка `Depends on:` в теле;
- ограничения: замороженные зоны (`AGENTS.md` §1: zero dependencies, протоколы
  адаптеров, обратная совместимость, compose.include).

Размер: S — дифф одним предложением; M — один модуль без смены интерфейсов;
L — несколько модулей/интерфейсы/новый модуль. Сомнение — в большую сторону.
Зависимости не закрыты — issue рождается сразу `status:blocked`.

## 2. Радиус аудита

Сам модуль + прямые зависимости (один уровень) + документация зоны + известный
долг. Транзитивные зависимости второго уровня — вне радиуса. Две `in-progress`
задачи с пересекающимся радиусом одновременно не живут — вторая в `blocked`.

## 3. Гейты ARCA

- AUDIT/RESEARCH ревьюит coordinator (или назначенный architect); CONCLUSION
  гейтишь всегда ты: решение понятно без чата, «Отвергнуто» заполнено (M/L),
  «Что меняю/НЕ меняю» точные, «Проверка» доказуема, объём по размеру.
- Гейт — сигнал `✅ GATE OPEN #N — phase:action открыт` (или `🔁 REJECTED #N —
  CONCLUSION: <причина>`), labels меняешь только ты.
- Координатор-исполнитель (пустая очередь, малая задача): гейт и ревью его
  поставки — другие агенты/сессии; сам себя не гейти и не ревьюй.
- Поставку, начатую до гейта, не признавай.

## 4. Мониторинг (после каждого значимого события)

1. Разблокировка: зависимости `done` → атомарно `status:ready`.
2. Label-repair: ровно один `status:*` (и один `phase:*` для M/L) на issue;
   при расхождении label и вердикта истина — вердикт в комментариях.
3. `blocked`/вопрос без движения дольше двух циклов — в сводку владельцу.
4. Stale-claim: нет движения дольше лимита размера (S=15 мин, M=60 мин, L=день) —
   `📣 PING #N`; ещё интервал тишины — `♻️ RECLAIMED #N`, задача обратно `ready`.
5. Счётчики (доля rejected, первая-приёмка) — по labels, на сводку владельцу.
6. Статусы/борд — вид поверх labels; расхождение чинится в сторону labels.

## 5. Ревью-цикл, слияние, приёмка

- Правки ревьювера → `status:rejected` + `to:<исполнитель>` + `🔁 REJECTED #N —
  итерация N/2: <первый пункт>`. Вторая rejected подряд — снять задачу с
  исполнителя, пересмотреть бриф; продуктовая проблема — эскалация владельцу.
- Слияние — только точный head-коммит из approve ревьювера; после слияния —
  полный регресс на результате и merge-пост (что влито, диапазон, чем проверено).
- Приёмка: продуктовое — только владелец (`status:review` + `needs-human`,
  сигнал `👤 NEEDS-HUMAN #N`); инфраструктурное (процессные доки, шаблоны, CI)
  координатор может принять сам — `🏁 DONE #N — <итог>`, владельцу сводка.
  При закрытии снимаются активные `status:*`, `to:*`, `phase:*`, `needs-human`.

## 6. Уровни окружения (отображение проекта)

| Уровень канона | Механика mock-services |
|---|---|
| test | ветка поставки + зелёный `npm test` и CI на PR |
| staging | `main` после слияния PR (push в `main` — smoke-джоба) |
| production | теги `v*` (полная матрица + docker; публикация образов GHCR только по тегам) |

Постановка в production — тот же SHA, что прошёл приёмку; обход уровней запрещён
(исключение — HOTFIX, объявляет только координатор, ревью не отменяется).

## 7. Launch-пакеты и вопросы

Внешнего исполнителя запускает владелец; координатор публикует самодостаточный
пакет (роль «КТО ТЫ», где что лежит, задача, радиус, ветка test, ограничения) +
флаг `launch-ready`. Секреты, креды и внутренняя инфраструктура в пакете и issues
запрещены всегда. Вопросы — отдельным question-issue (`type:question`), адресат —
`to:*`; отвечает и закрывает тот, кому адресован; ответ «решай в рамках радиуса»
легитимен, если записан явно.
