# Бриф: мок Т-Банка на всех контурах (локальный стенд / стейдж / прод)

**Дата:** 2026-09-28 · **Роль:** системная задача — по решению владельца отдаётся **Super Z**
(диктовка 28.09: «надо научиться его поднимать на локальном стенде, стейджинге и на проде,
это системная задача — её надо отдать Super Z, я думаю он разберётся»).

## Зачем

Платёжные потоки (верификация МСП, подписки, переводы) завязаны на вебхуки банка.
Мок уже один раз стоил инцидента (сессия 065: вебхуки падали из-за round-robin по алиасу
`app`) — нужен воспроизводимый, документированный запуск на всех трёх контурах.

## Что известно сейчас

- Мок живёт контейнером `tbank-mock` (порт 3100), health `ok:true`; переключение — env
  (`PAYMENTS_FAKE`, `TBANK_API_URL`); конфиг читается из env (`config/payments.php`), не из БД.
- Локально вебхуки починены 28.09: `TBANK_*_NOTIFICATION_URL` обязаны смотреть на **уникальное
  имя контейнера** приложения (алиас `app` шарится тремя контейнерами → 404).
- **Нет персистентности**: `MOCK_STATE_FILE` не задан — состояние мока теряется при рестарте.
- Открыт вопрос владельца: алиас `MTBANK` вместо имени контейнера (свободен, не применён).
- Состав и волны API мока — в `artifacts/RES-007-tbank-multisplit-mock-stand.md`.

## Что нужно сделать

1. **Инвентаризация по контурам.** Где мок живёт / должен жить на локальном стенде, на стейдже
   и на проде; чем отличается конфигурация; как переключается с реального банка на мок и обратно.
2. **Воспроизводимый подъём.** Локально — одной командой (профиль compose / скрипт), с health-чеком;
   стейдж — отработать порядок (мок поднимается вместе со стендом или отдельно, переживает ли деплой);
   прод — определить политику (мок на проде НЕ должен работать; явный запрет/флаг).
3. **Вебхуки.** Закрепить правило «уникальное имя контейнера», вынести в доки + проверку
   (smoke: сквозной платёж init → confirm → вебхук → статус).
4. **Персистентность мока** (файл состояния) + перезапуск без потери сценариев.
5. **Инструкция «как прогнать платёж/выплату»** на каждом контуре + типовые ошибки.
6. Решить по алиасу (`MTBANK` или имя контейнера) — внести решение.

## Критерий готовности

Инструкция и конфиги на все три контура; сквозной платёж на локальном стенде — по шагам;
на стейдже — воспроизводимо после деплоя; на проде — мок гарантированно вне игры;
решение по алиасу зафиксировано. Ссылки: сессия 065 (core), ПУШ-ПЛАН, RES-007.
