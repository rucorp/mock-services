# RES-007 — Т-Банк «Мультирасчеты»: выбор методов API + собственный тестовый стенд (мок банка)

Дата: 2026-09-19 · Автор: zcode · Статус: на утверждении владельца
База кода: core staging cc4e18d (спека `lovii-core/docs/specs/tbank-payments.md`, config/payments.php)

## 1. Задача и развязка

Владелец: «создать тестовый стенд вместо тестового стенда банка» — собрать информацию
по API (developer.tbank.ru) и выбрать полезные методы.

**Почему не реальный тестовый контур Т-Банка (сразу):**
- Доступ к нему дают **после подписания договора** (письмо менеджера, «Терминал Тбанк.md»);
- Запросы на тестовую среду требуют **IP-whitelist** (acq_help@tbank.ru) — а наш сервер за
  NAT/шарингом IP; для acqapi (регистрация точек) дополнительно **mTLS**;
- По докам каждого метода: на тестовую среду запросы надо отправлять **с боевого терминала**
  (риск наступать на боевой контур во время отладки).

**Решение: собственный мок-стенд банка** — маленький standalone-сервис, повторяющий
контракт Т-Банка (URL, payload, Token-подпись, статусы, нотификации, платёжная форма).
Эффекты:
- сквозной сценарий «оплата → вебхук → заказ → пул/кэшбэк» гоняется на staging без банка;
- переход на реальный тестовый/боевой контур = замена `TBANK_API_URL` в env, ноль правок кода;
- отказы, ретраи нотификаций, дубли, чарджбэк-зеркало — тестируются управляемо, а не «когда банк пришлёт».

Примечание: слово «текстовый стенд» из формулировки владельца прочитано как «тестовый стенд»;
в дизайн при этом заложена и текстовая админ-консоль (см. §6.4) — двойное назначение.

## 2. Продукт «Мультирасчеты» — как он устроен

Наш терминал — именно Мультисплит (договор №МР-08.26/АКС_01, ООО «АКСИОМА», MCC 7372),
это маркетплейс-продукт, а не обычный эквайринг:

- **Площадка** = lovii (терминал АКСИОМЫ) принимает оплату Покупателя и держит деньги
  **на Сделке**; после оказания услуги инициирует **Выплату Продавцу** (= мерчант/точка lovii)
  и берёт свою комиссию. Это ровно финконтур lovii: пул 40/40/20, 90% точке, 10% платформе.
- **Сделка (Deal / SpAccumulation)**: `Инициализация → Открыта → Частично отменена → Закрыта`.
  Баланс сделки = Σ CONFIRMED платежей − Σ выплат. Валидации банка (§4.1 продукт-доки):
  выплата только по существующей сделке, только после успешного списания (CONFIRMED),
  сумма выплаты ≤ остатка сделки, закрытие один раз, возврат покупателю после закрытия запрещён.
  Срок жизни сделки — договор п.1.7.11 (по умолчанию авто-отмена оплат через 60 дней от
  авторизации, если сделка не закрыта; банк авто-подтверждает холд через 4/7 дней — уточнить).
- **N списаний : N выплат** (§6.1 — наш вариант, форма банка, не PCI DSS):
  1. `/v2/Init` c `CreateDealWithType=NN` (вне блока DATA) → PaymentURL; о PlataformId/DealId
     в ответе при схеме с формой банка **DealId не возвращается** — он приходит
     **в нотификации AUTHORIZED параметром `SpAccumulationId`**;
  2. покупатель платит на форме банка → холд → нотификация AUTHORIZED (+SpAccumulationId);
  3. площадка вызывает `/v2/Confirm` → списание → нотификация CONFIRMED;
  4. выплата: `/e2c/v2/Init` (DealId, Amount ≤ баланса сделки, `FinalPayout=true` вне DATA —
     закрывает сделку) → `/e2c/v2/Payment` (PaymentId из ответа) → COMPLETED;
  5. повторные выплаты — в рамках остатка сделки.
- **Каналы выплаты** (комиссия из письма менеджера): ЮЛ — «перечисление третьему лицу»
  (`PartnerId` = shopCode зарегистрированной точки) — 0,5%; ФЛ/самозанятые — СБП
  (`Phone`+`SbpMemberId`) или карта (`CardId`/`CardData`) — 1%, мин. 30 ₽.
- **Регистрация точек партнёров** (acqapi, mTLS+IP-WL): `POST /oauth/token` (Basic
  `partner:partner`, grant_type=password, логин/пароль выдаёт банк) → `POST /sm-register/register`
  (полные реквизиты ЮЛ, ИНН/КПП/ОГРН, адреса, CEO, bankAccount, шаблон назначения платежа
  «по Реестру Операций от $(date). Сумма комиссии $(rub) руб. $(kop) коп.») → ответ
  `{code, shopCode}`; далее `GET /sm-register/register/shop/{shopCode}` и `PATCH` на обновление.

## 3. Выбранные методы (что мокаем и в каком порядке)

### Волна 1 — оплата заказа (закрывает существующий код core без правок)

| Метод | Зачем нам | Кто вызывает |
|---|---|---|
| `POST /v2/Init` | старт платежа: TerminalKey, Amount (копейки), OrderId (`{order_id}-{payment_id}`), Token, PayType=T (двухстадийный), CreateDealWithType=NN, PaymentRecipientId, CustomerKey, NotificationURL/SuccessURL/FailURL (у нас с `{order_id}`), RedirectDueDate, DATA, Descriptor | core `TBankClient::init` |
| `POST /v2/Confirm` | списание холда после передачи заказа (сумма ≤ авторизованной) | core `TBankClient::confirm` (метод есть, вызовов пока нет — см. §7) |
| `POST /v2/Cancel` | отмена/возврат: NEW→CANCELED, AUTHORIZED→REVERSED/PARTIAL_REVERSED, CONFIRMED→REFUNDED/PARTIAL_REFUNDED | core `TBankClient::cancel` (на будущее) |
| `POST /v2/GetState` | сервер-сервер источник истины — core дёргает его на каждый вебхук, телу вебхука не доверяет | core `TBankClient::getState` |
| `POST /v2/CheckOrder` | сверка всех попыток по OrderId (для §5.4 сверок и дебага) | новое (админка/сверка) |
| **Нотификации** `POST → core /api/v1/payments/tbank/webhook` | payload: TerminalKey, OrderId, Success, Status, PaymentId, ErrorCode, Amount, CardId, Pan, ExpDate, RebillId, **SpAccumulationId** (мультисплит), DATA, Token. Ответ строго `OK`; иначе ретрай раз в час 24 ч | мок → core |

Статусы оплаты, которые эмулирует стенд (и их маппинг в `PaymentStatus` core —
`fromBankStatus` уже покрывает все): NEW, FORM_SHOWED, AUTHORIZING, 3DS_CHECKING,
3DS_CHECKED, AUTHORIZING→AUTHORIZED, PAY_CHECKING, CONFIRMING/CONFIRM_CHECKING,
CONFIRMED, REVERSING/REVERSED, PARTIAL_REVERSED, REFUNDING/ASYNC_REFUNDING,
PARTIAL_REFUNDED, REFUNDED, CANCELED, DEADLINE_EXPIRED, REJECTED, AUTH_FAIL.
Чарджбэк-статусы в оплата-доке Мультисплита **не описаны** (в нотификациях их нет) —
уточнить у менеджера; core-маппинг `PARTIAL_CHARGEBACK→Chargeback` уже готов (решение №8).

### Волна 2 — выплаты точкам (когда владелец даст «го» на выплаты)

`POST /e2c/v2/Init` (DealId обязателен, канал: PartnerId / Phone+SbpMemberId / CardId),
`POST /e2c/v2/Payment`, `POST /e2c/v2/GetState`, `POST /e2c/v2/CancelPayment`
(CREDIT_CANCELING→CREDIT_CANCELED), `POST /e2c/v2/GetSbpMembers`.
Статусы выплаты: NEW, CHECKING, CHECKED, COMPLETING, **COMPLETED**, **REJECTED**, CREDIT_CHECKING.
Подпись выплат: Token (если валидация подписи у банка отключена) **или** RSA-набор
`DigestValue` (base64(sha256)) + `SignatureValue` (RSA-SHA256) + `X509SerialNumber`; для мока
принимаем Token-режим (включение/отключение валидации — по договорённости с банком).
Стенд ведёт **книгу сделок** с валидациями §4.1 — именно она проверит нашу финансовую логику.

### Волна 3 — по мере нужды (не мокаем сейчас)

- `/v2/createSpDeal`, `/v2/closeSpDeal` — альтернативное управление сделкой (наш путь — CreateDealWithType);
- привязка карт и рекуррент: AddCustomer/GetCustomer/RemoveCustomer/AddCard/AttachCard/
  GetAddCardState/GetCardList/RemoveCard + нотификация LINKCARD + `Charge` (RebillId) —
  понадобится, если подписка PASS вернётся на карту (сейчас — внутренний счёт, решение 18.09);
- СБП-QR: GetQr, QrMembersList, ChargeQr и т.д.;
- acqapi `/oauth/token`, `/sm-register/register` (+GET/PATCH) — когда автоматизируем
  онбординг точек (сейчас точки заводит банк по заявкам).

## 4. Подпись (Token) — единый алгоритм, у нас уже реализован

Token = sha256(конкатенация значений всех параметров, кроме Token/Receipt/массивов/null/'',
отсортированных по ключу, bool → lowercase, плюс Password). Реализация в core —
`TBankSignature` — сверена с докой, совпадает. **Важно для мультисплита: `SpAccumulationId`
участвует в Token нотификации** — мок обязан это соблюдать, иначе проверка подписи в core
завалится (годный негативный тест). Обязательность Token в запросах включается у банка по
запросу; мок включает всегда.

| 2200770239097761 / 4249170392197566 / 5586200071492075 | без 3DS: успех / недостаточно средств / ошибка списания |

Выплата: `5000000000000447` — успех; `5000000000000553` — отказ `authRC=1057`
(«Покупатель запретил такие операции») в ответ на Payment.

Сценарии стендовых сбоев (инъекция): таймаут ответа, `Success=false` на Confirm/Cancel,
не-`OK` ответ на нотификацию → ретраи (интервалы сжаты: 1 мин × N вместо часа),
дубли нотификации (идемпотентность core), авто-подтверждение холда по таймеру
(4/7 дней → ускоренный режим), DEADLINE_EXPIRED по RedirectDueDate.

## 6. Архитектура мок-стенда

### 6.1 Форма и размещение
- **Standalone HTTP-сервис** (Node/TS или PHP), живёт в репо `lovii-core` (папка
  `tbank-mock/` + сервис в docker-compose; новых репо не заводим — правило из Т-Банк-контекста).
  На staging — отдельный контейнер рядом с core, наружу не торчит (nginx allowlist / только
  из внутренней сети); в проде отсутствует по построению (env staging-only).
- Конфиг: фейковые TerminalKey/Password (те же значения в env core и стенда).

### 6.2 Компоненты
1. **API банка**: `/v2/{Init,Confirm,Cancel,GetState,CheckOrder,createSpDeal,closeSpDeal}` и
   `/e2c/v2/{Init,Payment,GetState,CancelPayment,GetSbpMembers}` — контракты из §3–5.
2. **Эмулятор платёжной формы** (страница PaymentURL): ввод карты/срока/CVV, выбор сценария
   по PAN (см. §5), challenge-экран с OTP — реальный браузерный редирект
   SuccessURL/FailURL работает как у банка.
3. **Нотификатор**: на каждом переходе статуса POST подписанного уведомления на
   NotificationURL из Init, ожидание `OK`, очередь ретраев, журнал доставки.
4. **Книга операций**: платежи (PaymentId, OrderId, Amount, Status, DealId, маска PAN, CardId)
   и сделки (баланс, статус, FinalPayout) — sqlite/файл, достаточно.
5. **Валидации банк-стороны**: Token обязателен и сверяется; Confirm только из AUTHORIZED;
   Cancel по таблице переходов; выплата ≤ баланса сделки и только после CONFIRMED;
   FinalPayout один раз; возврат после закрытия сделки запрещён; PaymentId неизвестен →
   `Success=false`, ErrorCode ≠ 0.

### 6.3 Почему не дорабатывать FakeTBankClient
Внутрипроцессный фейк (`FakeTBankClient` + страница `/payment/fake` в app +
`/payments/fake/notify`) остаётся для дешёвых локальных прогонов — он не ходит по HTTP,
не шлёт настоящие нотификации и не проверяет подпись/редиректы/ретраи. Мок-стенд —
это «настоящий банк» на HTTP: core работает через обычный `TBankClient`, вебхуки приходят
снаружи, проверка Token в `HandleTBankNotificationAction` выполняется по-настоящему.
Переключение стенд↔банк — только env: `TBANK_API_URL` (у нас это `env` в
config/payments.php:45). UI в app не меняется вообще.

### 6.4 Текстовая админ-консоль (вторая половина названия «текстовый стенд»)
Минимальный CLI/HTML: список платежей и сделок с балансами, ручной перевод статуса
(«подтвердить холд как банк», «закрыть сделку остатком»), инъекция сбоев (§5),
повтор/просмотр нотификаций и ответов core. Этого хватает для приёмки и демо без UI-канона.

## 7. Дельта в core (небольшая, отдельно от стенда)

1. **`SpAccumulationId` → `payments.deal_id`**: сейчас DealId сохраняется только из ответа
   Init (`CreateOrderPaymentAction`), но в схеме с формой банка банк его в ответе не отдаёт —
   идентификатор сделки приходит только в нотификации AUTHORIZED. Добавить запись в
   `HandleTBankNotificationAction`. Без этого выплата по сделке (волна 2) не соберётся.
2. **Вызов Confirm**: `TBankClient::confirm` реализован, но не вызывается никем
   (авто-подтверждение отложено до фискализации I-1). Для волны 1 нужен момент вызова:
   по передаче заказа / вручную из админки — решение владельца.
3. Выплаты (клиент e2c) — отдельная фича волны 2; финмодель уже в каноне
   (FINANCIAL_MODEL §2 / PARAMS §1.2, ЮЛ 0,5% / ФЛ 1% мин 30 ₽).

Волне 1 ничего из этого не блокирует: сквозняк «Init → форма → AUTHORIZED-нотификация →
GetState → CONFIRMED» работает на текущем коде.

## 8. План реализации (черновой, по «го» владельца)

1. **Мок-стенд, волна 1**: API Init/GetState/Confirm/Cancel/CheckOrder + форма + нотификатор
   + админ-консоль; прогон e2e «заказ → оплата → заказ submitted → кэшбэк → пул» на staging.
2. **Дельта core** (SpAccumulationId + решение по Confirm) — той же веткой либо следом.
3. **Волна 2 (выплаты)**: книга сделок + e2c-методы + клиент e2c в core; пилот выплат
   «перечисление третьему лицу» (PartnerId) на свои ЮЛ владельца.
4. Волна 3 — по мере появления решений (рекуррент PASS, СБП, авто-регистрация точек).
