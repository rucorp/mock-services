# ЮKassa — вебхуки и сверка статуса

Первичный источник — [официальная документация уведомлений](https://yookassa.ru/developers/using-api/webhooks); формат объектов — [OpenAPI](https://yookassa.ru/developers/using-api/openapi-specification).

## Формат

Уведомление — входящий HTTP `POST` с JSON-объектом, содержащим `type` (событие), `event` (например, `payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled` или `refund.succeeded`) и `object` (платёж или возврат с `id`, `status`, суммой и метаданными). Настроить endpoint в личном кабинете; события могут быть доставлены повторно.

Уведомления отправляются повторно при недоступности endpoint, в течение периода до 24 часов; успешным ACK является HTTP `200`. Полагаться на точное число/интервал повторов нельзя, так как публичная инструкция задаёт повторную доставку, а не стабильный таймерный контракт.

## Подлинность и обработка

В публичном формате webhook нет криптографической подписи, которую получатель мог бы проверить локально. Использовать webhook как сигнал для сверки, а не как единственный источник истины:

1. Проверить, что `object.id` относится к известной ожидаемой операции.
2. Запросить `GET /payments/{id}` либо `GET /refunds/{id}` с серверными API credentials.
3. Проверить тип события, финальный `status`, сумму/валюту и собственную связь с заказом.
4. Ответить `200` после надёжного приёма события; дедуплицировать по идентификатору объекта + событию, поскольку доставка может повторяться.

Если нужна дополнительная транспортная защита, ограничивать вход по опубликованным ЮKassa IP и по TLS, но это не заменяет сверку объекта через API.

## Отличие от существующего мока

Т-Банк-мок моделирует Token-подпись и ждёт тело `OK`; ЮKassa шлёт объектное JSON-событие и ожидает HTTP 200. Не валидировать webhook ЮKassa алгоритмом Token/HMAC из tbank-mock.
