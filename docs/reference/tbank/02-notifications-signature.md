# Конспект: http-нотификации и подпись (Token)

Источник: `docs/oplata_multisplit.pdf` §3–4, `docs/multisplit.pdf` §5, 24. Конспект — неофициальный.

## Http(s)-нотификации

Банк шлёт `POST` на `NotificationURL` (настройка терминала или параметр `Init`) при операциях
Authorize / FinishAuthorize / Confirm / Cancel / Charge.

- Ответ площадки при успешной обработке: HTTP 200 и тело ровно **`OK`** (заглавными,
  без тегов). Иначе нотификация считается недоставленной: ретрай **раз в час в течение
  24 часов**, затем складывается в дамп.
- Допустимый порт для NotificationURL — только **443**.
- Сети, с которых приходят уведомления (добавить в allowlist фильтров):
  `91.194.226.0/23`, `91.218.132.0/22`, `212.233.80.0/22`.

Рекомендуемые проверки перед обработкой: сеть отправителя, Token, сумма платежа,
TerminalKey, OrderId. **Тело нотификации не источник истины** — надёжнее проверить
подпись и перезапросить статус через `GetState` (сервер-сервер).

### Параметры нотификации

| Параметр | Описание |
|---|---|
| `TerminalKey` | ключ терминала |
| `OrderId` | номер заказа площадки |
| `Success` | bool |
| `Status` | статус транзакции |
| `PaymentId` | идентификатор платежа в банке |
| `ErrorCode` | `0` при успехе |
| `Amount` | текущая сумма транзакции в копейках |
| `CardId`, `Pan`, `ExpDate` | карта: id, замаскированный номер (`430000**0777`), срок |
| `RebillId` | идентификатор рекуррента (если `Recurrent=Y` в Init) |
| `SpAccumulationId` | **идентификатор Сделки (Мультисплит)** — приходит в нотификации `AUTHORIZED`, когда сделка создавалась через `CreateDealWithType=NN` |
| `DATA` | доп. параметры, переданные в Init |
| `Token` | подпись (алгоритм ниже) |

### Статусы, по которым приходят нотификации

`AUTHORIZED`, `CONFIRMED`, `REVERSED`, `REFUNDED`, `PARTIAL_REFUNDED`, `REJECTED`,
а также автозакрытие 3DS-сессий (`3DS_CHECKING`/`DEADLINE_EXPIRED` — включается по
запросу в поддержку).

⚠️ Чарджбэк-нотификации в оплатной доке Мультисплита не описаны — уточнять у банка
(статусы `CHARGEBACK`/`PARTIAL_CHARGEBACK` встречаются в практике интеграций).

## Алгоритм подписи Token

1. Взять все параметры пары «ключ-значение», **кроме** `Token` (и вложенных структур —
   `Receipt`, `DATA`, массивов); `null` и пустые строки пропускаются.
2. Добавить пару `Password` = пароль терминала (из ЛК business.tbank.ru).
3. Отсортировать по ключам алфавитно.
4. Конкатенировать **значения** (bool — строкой в нижнем регистре `true`/`false`).
5. `Token = sha256(конкатенация)` в hex.

Пример из доки: значения `985532226401122201709430000******0777Dfsfh56dgKl8742591101709AUTHORIZEDtrue1321054611234DEMO`
→ `b906d28e76c6428e37b25fcf86c0adc52c63d503013fdd632e300593d165766b`.

**Мультисплит-специфика:** `SpAccumulationId` — скаляр, он **участвует** в Token
нотификации. Если площадка хранит сделку, но не учитывает этот параметр при проверке
подписи — проверка будет падать.

Обязательность валидации Token в запросах к банку включается по запросу в поддержку
(acq_help@tbank.ru).

## Подпись выплатных (e2c) запросов

Три варианта (выплаты):

1. **Token** — тот же алгоритм, но параметры `X509SerialNumber`, `DigestValue`,
   `SignatureValue` в подписи не участвуют. Применимо, если у терминала отключена
   валидация сертификатом (переключение — по договорённости с банком).
2. **RSA-сертификат**: собрать параметры (без `DigestValue`/`SignatureValue`/`X509SerialNumber`),
   отсортировать, конкатенировать значения → `DigestValue = base64(sha256(bytes))`;
   `SignatureValue = base64(RSA-SHA256-sign(bytes))`; передать серийник в `X509SerialNumber`.
3. **КриптоПро (ГОСТ)**: хэш ГОСТ Р 34.11-2012 256 в `DigestValue`, подпись ГОСТ Р 34.10-2012 256 в `SignatureValue`.
