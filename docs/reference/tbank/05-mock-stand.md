# Конспект: мок-стенд Т-Банка (тестовый контур своими руками)

Конспект-паттерн из практики интеграции lovii. Неофициальный.

## Зачем

Реальный тестовый контур Т-Банка — не «включил и тестируешь»:

- доступ к тестовой среде дают **после подписания договора**, IP сервера надо вносить
  в whitelist (acq_help@tbank.ru), для acqapi дополнительно **mTLS**;
- по документации каждого метода запросы на тестовую среду надо отправлять
  **с боевого терминала** — отладка наступает на боевой контур;
- отказы, ретраи нотификаций, дубли, чарджбэки — «когда банк пришлёт», не управляемо.

Мок-стенд решает это: маленький standalone-сервис, повторяющий контракт банка
(URL, payload, Token-подпись, статусы, нотификации, платёжная форма). Переход на
реальный контур — замена одного env-параметра (`api_url`), код площадки не меняется.

## Компоненты

1. **API банка**: `/v2/{Init, Confirm, Cancel, GetState, CheckOrder, createSpDeal,
   closeSpDeal}` и `/e2c/v2/{Init, Payment, GetState, CancelPayment, GetSbpMembers}`.
   Валидации как у банка: Token обязателен и сверяется; `Confirm` только из
   `AUTHORIZED`; `Cancel` по таблице переходов; выплата ≤ баланса сделки и только после
   `CONFIRMED`; `FinalPayout` один раз; возврат после закрытия сделки запрещён;
   неизвестный `PaymentId` → `Success=false`, ErrorCode ≠ 0.
2. **Эмулятор платёжной формы** — страница `PaymentURL`: ввод карты/срока/CVV, сценарий
   по PAN (см. notes/04-test-cards.md), challenge-экран с OTP. Реальный браузерный
   редирект SuccessURL/FailURL работает как у банка.
3. **Нотификатор**: на каждом переходе статуса — подписанный `POST` на `NotificationURL`
   из Init; ожидание тела `OK`; очередь ретраев (для тестов интервалы сжаты: минуты
   вместо часа); журнал доставок.
4. **Книга операций**: платежи (PaymentId, OrderId, Amount, Status, DealId, маска PAN,
   CardId) и сделки (баланс, статус, FinalPayout) — sqlite достаточно.
5. **Админ-консоль** (CLI или минимальный HTML): список операций, ручные переходы
   статусов («банк подтвердил холд», «закрыть сделку остатком»), инъекция сбоев
   (таймаут, `Success=false`, не-`OK` ответ площадки, дубли нотификаций,
   авто-подтверждение холда по таймеру, `DEADLINE_EXPIRED`).

## Ключевые тонкости, которые мок должен соблюдать

- `SpAccumulationId` приходит **только в нотификации AUTHORIZED** (не в ответе Init) и
  **участвует в Token** нотификации;
- Token: отсортированные значения (без Token/вложенных структур/null/''), bool в
  lowercase, + Password, sha256;
- ответ площадки на нотификацию — ровно `OK`, иначе ретраи (у банка: раз в час, 24 часа);
- сумма Confirm ≤ суммы авторизации; частичные REVERSED/REFUNDED;
- `ExternalRequestId` в Cancel — идемпотентность возвратов;
- сделка: баланс, один FinalPayout, запрет возвратов после закрытия, срок жизни.

## Подключение площадки

Площадка продолжает работать через обычного HTTP-клиента банка; меняется только
базовый URL и (опционально) адрес страницы фейкового терминала. Внутрипроцессные
фейки («мгновенно успешный Init») полезны для локальных прогонов, но не проверяют
подпись, редиректы, ретраи и настоящие вебхуки — мок-стенд это закрывает.

## Безопасность

- фейковые TerminalKey/Password (одинаковые в env площадки и мока);
- мок не должен быть доступен из интернета (внутренняя сеть / allowlist);
- в production-окружении мок отсутствует по построению (env-гейтинг).
