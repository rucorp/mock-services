## Авторизация

`POST /API/v2/Login`, JSON, заголовки `Integrator-ID: <ID>` и `Content-Type: application/json`. Тело должно соответствовать официальной схеме `Login_Request` из приложения к API Help; документация страницы с методом ссылается на схему, но не раскрывает её поля inline. **Не выдумывать** тело по старым SDK/сторонним примерам. Уточнить актуальный JSON schema archive у Такском/в кабинете до реализации.

Ответ содержит временный marker; все дальнейшие вызовы несут его в заголовке `Session-Token`. TTL — пять минут после получения или последнего использования (sliding). Повторный Login не выдаёт новый marker, пока предыдущий действителен. Просроченный token даёт HTTP 401.

## Методы discovery и чтения

| Метод | Назначение |
|---|---|
| `GET /API/v2/AccountList` | Договоры/личные кабинеты, доступные пользователю и его права. |
| `GET /API/v2/NewDocuments` | Поток новых фискальных документов за последние 10 суток, курсор по ID. |

`NewDocuments` возвращает фискальные документы (чеки/возвраты/коррекции, смены и БСО) как данные, уже принятые ОФД. Другие методы Такском API перечислены в help; здесь указаны только маршруты/схемы, подтверждённые в доступной HTML-документации. Запросы на чтение используют `Session-Token`; `Integrator-ID` выдаётся поддержкой. Роли пользователя ограничивают видимые кабинеты/кассы/документы.

## Не путать с передачей чеков

API Help описывает работу с личным кабинетом, ККТ и **чтение уже полученных ОФД фискальных документов**. По опубликованной части API v2.17 не найден публичный метод создания/фискализации чека, возврата чека, асинхронного callback результата или платежный webhook. Не делать вывод, что эти методы существуют в частном кабинете; для задач печати нужен подтверждённый отдельный продукт/контракт.
