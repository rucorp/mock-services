# Сбер — интернет-эквайринг: REST API

Срез официальной документации на 2026-10-11. Здесь описан актуальный шлюз Ecom из портала `ecomtest.sberbank.ru`, а не старый Secure Payments API.

## Первичные источники

- [Официальный портал API шлюза Ecom](https://ecomtest.sberbank.ru/doc) — на дату среза версия 1.1.11.1; разделы «Обработка сообщений», сервисы работы с заказом и callback.
- [OpenAPI YAML шлюза](https://ecomtest.sberbank.ru/yaml/ecom.yaml).
- [Официальное текстовое описание orderStatus в REST API](https://developer.sberbank.ru/doc/v1/acquiring/rest-requests1pay) — использовать только для сверки терминов/значений статуса; это не альтернативный endpoint для нового Ecom API.

## Транспорт и доступ

| Контур | API base |
|---|---|
| Тест | `https://ecomtest.sberbank.ru/ecomm/gw/partner/api/v1/` |
| Production | `https://epay.sberbank.ru/ecomm/gw/partner/api/v1/` |

Каждый сервис вызывается `POST`; `Content-Type: application/json`, UTF-8. Ключи JSON чувствительны к регистру. Не передавать `null`: отсутствующее необязательное значение нужно опустить. TLS 1.2/1.3; официальный раздел подключения также требует установить сертификат НУЦ Минцифры. `userName` и `password` выдаются после подключения партнёра. API работает с суммами в минимальных единицах валюты (для RUB — копейки).

## Основной поток

1. `POST register.do` создаёт заказ для одностадийного платежа с переходом на hosted payment page; `POST registerPreAuth.do` создаёт заказ для двухстадийной оплаты/холда (функция подключается банком отдельно). Минимально нужны `userName`, `password`, уникальный `orderNumber`, `amount`, `returnUrl`. Обычно также задают `currency` (`643` для RUB), `failUrl`, `description`, `email` покупателя и/или `sessionTimeoutSecs`. Заказ возвращает `orderId` и `formUrl`; браузер покупателя перенаправляют на `formUrl`.
2. `POST paymentOrder.do` — прямое проведение карточной оплаты по ранее зарегистрированному заказу с карточными реквизитами; доступность зависит от разрешений мерчанта. Не путать этот server-to-server сценарий с перенаправлением на `formUrl`.
3. Для двухстадийной схемы `POST deposit.do` завершает холд и списывает подтверждаемую сумму, не превышающую авторизованную. Банк рекомендует провести расчёты в пределах семи календарных дней.
4. `POST reverse.do` отменяет авторизацию/заказ до начала взаиморасчётов; для одностадийной оплаты доступно примерно до конца банковского дня, для двухстадийной — только до `deposit`. `POST refund.do` возвращает полностью или частично уже списанные средства после начала взаиморасчётов; это не то же самое, что reversal.
5. `POST decline.do` отменяет заказ до того, как плательщик начал вводить карточные данные.
6. `POST getOrderStatusExtended.do` — запрос состояния по `orderId`, серверная проверка результата и источник истины после редиректа или callback.

У сервисов есть и другие необязательные поля и сценарии (например, корзина `orderBundle`, привязанные карты, SberPay/СБП); их следует добавлять только при наличии соответствующего merchant-разрешения. `errorCode = 0` означает, что запрос обработан шлюзом без системной ошибки, но само по себе **не доказывает**, что оплата успешна: проверять `orderStatus`/состояние операции.

### Состояния заказа из базовой документации

В текущем Ecom-портале диаграмма [состояний заказа](https://ecomtest.sberbank.ru/img/state_orderStatus.png) опубликована только как изображение и не извлекается текстом. Таблица ниже совпадает с текстовым описанием статусов в официальной документации REST; перед реализацией её всё равно нужно визуально сверить с диаграммой и тестовым ответом именно подключённого Ecom-мерчанта. Не путать `orderStatus` со статусом операции `actionCode`.

| `orderStatus` | Значение |
|---:|---|
| 0 | заказ зарегистрирован, не оплачен |
| 1 | сумма захолдирована (двухстадийная схема) |
| 2 | полная авторизация/оплата проведена |
| 3 | авторизация отменена |
| 4 | по заказу проведён возврат |
| 5 | начата аутентификация через ACS эмитента |
| 6 | авторизация отклонена |

Заказ по умолчанию живёт 20 минут; срок можно задать при регистрации. У заказа до истечения срока — три попытки оплаты. Не сводить все промежуточные результаты 3DS к финальному состоянию.

## Отличие от имеющегося `tbank-mock`

В репозитории реализован контракт Т-Банка `POST /v2/Init|Confirm|Cancel|GetState|CheckOrder`, подпись `Token` и собственный набор статусов (`AUTHORIZED`, `CONFIRMED` и др.). Сбер использует `.../ecomm/gw/partner/api/v1/*.do`, JSON с `userName/password`, `orderId` и собственные числовые `orderStatus`; форматы запросов/ответов, подписи и callback нельзя подменить контрактом Т-Банка. Общая только предметная модель «создать → статус → подтвердить/отменить/возвратить».
