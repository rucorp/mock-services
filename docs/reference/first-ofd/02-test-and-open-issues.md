# Первый ОФД — тестовый стенд и расхождения документации

Срез 2026-10-11. Источники: [актуальный manual OKassa (23.07.2026)](https://help.1-ofd.ru/upload/medialibrary/docs/oblachnaya_kassa_opisanie_api.pdf), [тестовый Swagger UI](https://external-api-farm.1-ofd-test.ru/swagger-ui/index.html), [OpenAPI 3.1 / 26.13.3](https://external-api-farm.1-ofd-test.ru/api/v3/spec), [информация разработчикам](https://1-ofd.ru/articles/razrabotchikam), [страница аренды облачной кассы](https://1-ofd.ru/rent-cloud-box).

## Что можно тестировать

Тестовый Swagger и OpenAPI доступны публично на `external-api-farm.1-ofd-test.ru`, но статические login/API-key UUID не опубликованы. Реквизиты берутся в тестовом личном кабинете/разделе интеграций; не использовать примеры UUID из схемы как реальные учётные данные. Не подтверждён публичный production API base.

Для smoke/selftest будущего адаптера минимально проверить: выдачу Bearer-токена; одну заявку `receipt`; возврат `INCOME_RETURN`; `requestId` → статусы; повторный `externalId` в той же группе; callback endpoint, если он настроен; сверку через `/receipts` за период.

## Явные противоречия manual и тестового OpenAPI

1. **Обязательность `requestMetadata`.** Manual описывает его как необязательное поле в одном разделе; тестовый OpenAPI у `ReceiptRequest` включает `requestMetadata` в `required`. До реального договора использовать строгую OpenAPI-схему для теста, но перед производственной реализацией получить подтверждение от Первого ОФД.
2. **Форма `document.items`.** Таблица manual трактует часть структуры как объект; OpenAPI описывает массив элементов. Не выбирать один вариант по аналогии с Ferma/АТОЛ; применять согласованную схему тестового/производственного API.
3. **Схема callback URL.** PDF говорит, что URL должен начинаться с `http://`, тогда как пример самого PDF и OpenAPI используют `https://`. Для production ориентироваться на HTTPS только после подтверждения при подключении.
4. **Пример успешного `getToken`.** В PDF под заголовком успешного ответа приведён объект `error` с кодом 0 и текстом «Неверный логин и пароль», хотя текст похож на ошибку и `token` должен возвращаться только при отсутствии ошибки. Для определения успеха требуется согласовать семантику `error` с провайдером; одного HTTP 200 недостаточно.
5. **Отдельный ATOL Online API в тестовом Swagger.** Это отдельные `/api/external/possystem/v5/...` методы с ATOL-операциями; они не заменяют OKassa `/api/external/queue/v1/...` и не меняют сферу документа.

## Что публично не установлено

Не удалось подтвердить публичные production URL и тестовые креды, подпись/ACK/retry callback, гарантии порядка доставки callback и точный срок хранения `requestId`/`externalId`. Эти детали не восполнять догадками; перед будущим адаптером получить доступ к test cabinet/production spec либо письменный ответ поддержки.
